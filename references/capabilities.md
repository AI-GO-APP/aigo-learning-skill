# 功能導覽與學生帳號的可用範圍

先問學生想做什麼、給誰用、目前最麻煩的是什麼，再用他的情境導覽。不要把課程綁定店家預約，更不要假設他有公司、要接案或已具特定產業與開發經驗。

| 想解決的事 | 可看的方向 | 最小練習 |
|---|---|---|
| 表格散落、重複抄寫 | 資料中心、內部清單、搜尋與狀態更新 | 三筆虛構資料，找到一筆並改狀態 |
| 不知道哪件事先處理 | 看板、逾期提醒、指標 | 手算逾期數，缺日期另列，再核對畫面 |
| 客人需要自己看介紹或送資料 | 公開 Hosted 網站＋內部處理畫面 | 看介紹→送申請→內部看到同一筆 |
| 文件很多、想找重點 | 知識中心、平台 AI；先確認資料及用量設定 | 用自己的虛構文件做摘要或找依據 |
| 每次都要做相同步驟 | Server Action、排程、外部串接 | 先手動跑一例，再討論排程及副作用 |
| 不知道從哪裡開始 | 已安裝範本或範本目錄 | 先查實際可用範本，再選一個畫面改一個條件 |

技術與範本清單向 Builder 查證；不能把展示案例當成已開通。沒有可用範本就從小題開始，不保證標準套件均已安裝。

## DnSchool 權限標準（2026-10-28）

開通標準為下列 11 個權限；實際以目前帳號的 `/auth/me` 與開通卡為準。這是功能範圍，不是資料隔離證明。只是討論時可先解釋標準，不必強迫登入；操作前才核對本人及實際權限。

| 權限 | 白話說法 |
|---|---|
| builder.access | 使用作品開發工具與獲授權的資料工具 |
| builder.manage_access | 設定本次自己作品的可見群組，仍須遵守課程範圍 |
| builder.publish | 發布自己的內部作品 |
| builder.app_cron_manage | 管理自己作品的排程，先確認測試與副作用 |
| hosted_apps.deploy | 建立及部署自己的對外網站 |
| datacenter.schema_write | 建立或調整練習所需資料結構；不包含任意刪除共享表 |
| files.access | 使用自己可見的檔案；仍受檔案權限限制 |
| ai.hub.invoke | 使用已設定、可用的 AI Hub；不代表額度無限或已附贈費用 |
| cowork.skill.manage | 管理本次自己的平台技能；不修改他人資源 |
| ai.access | 使用已開放的平台 AI 功能；用量與金鑰另核對 |
| announcements.read | 閱讀公告；沒有發布公告權限 |

不提供發布全體公告、角色／成員管理、任意升權或操作別人作品。平台內各業務模組頁面及 API，需額外對應模組權限；不要因為可以開發 App，就宣稱所有 CRM／財務頁面均已開放。App 經資料引用及伺服端授權可用哪些資料，另由 Builder 核對，不把兩種權限混為一談。

## 有問題先由 AI 排查

1. 開通資料：先看開通卡與既有非機密設定，缺哪一欄就說哪一欄；不要重問已給資料、猜編號或立刻轉給助教。資料確實未發放才需要開通人員補齊。
2. 權限問題：先區分未登入、選錯作品、資料引用缺少、帳號未含該功能、程式錯誤。已知未含功能就直接解釋限制及可行替代，不讓學生重裝或換帳號。
3. 工具／用量：先幫學生保留成果並處理本機問題、確認訂閱登入及使用量，不能自動改成 API 計費。
4. 系統故障只有 Builder 的平台問題回報管道：讀已安裝 Builder 的 references/issue-reporting.md，以證據排查設定、程式、權限、版本及平台，查既有卡、整理摘要，取得使用者送出確認後才用 scripts/report_issue.py submit。不要新增客服信箱、LINE、GitHub issue 或助教轉報渠道；查進度也走同一工具。開通卡真的缺資料才請原開通人員補齊，不把缺資料當平台故障。

期限、續約、價格、退費與資料隔離承諾不由 AI 臆測；沿用目前已核准的教材與合約，待定政策不寫成已確定。
